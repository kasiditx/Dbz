## Priority 1 — resize stall (~1,009 ms frame intervals)
**Loop used:** `benchmarks/followup/resize_experiments.py` (programmatic + AX-driven resize, per-frame CSV, stall = interval > 100 ms) and `resize_mouse.py` (real mouse drags via CGEvent on the window corner). Both deterministic enough to compare, seconds-to-minutes per case.

**Evidence, in order**
1. `sample` of the app during the stall (`raw/sample_resize_stall.txt`): main thread parked in `-[CAMetalLayer nextDrawable]` → `_dispatch_semaphore_wait_slow` for **4267 of 4635 samples (92 %)**, called from `wgpu Surface::get_current_texture` ← `egui_wgpu Painter::paint_and_update_textures` ← `winit WinitView::draw_rect` ← `NSViewBackingLayer display` ← `CA::Transaction::commit`. I.e. the redraw runs *inside* AppKit's transaction commit and blocks waiting for a drawable. `ui()` itself costs 0.2–0.8 ms in those frames, so the time is **outside egui's `ui()`**, in AppKit/CoreAnimation/wgpu presentation. The stall length (1008–1033 ms; 749 and 255 ms outliers) matches CAMetalLayer's 1 s `nextDrawable` wait.
2. Source: egui-wgpu enables by default `macos-window-resize-jitter-fix`, which turns on `presentsWithTransaction` and 3 drawables while `resizing` (egui-wgpu `winit.rs`, comment "Transaction presentation can hold a drawable during AppKit live resize").
3. Programmatic resize frequency (`--resize-every N`, 120 frames, 100k rows): every frame → **21 stalls / 122 frames (21.2 s stalled)** in one run, 2 in a repeat; every 5th frame → **0**; every 30th → **0**. So the harness's original resize-every-frame loop is a stress pattern, not typical use.
4. OS-driven resize from another process (System Events `set size`, 40 steps ×8 runs per variant, base build): stalls in **5/8 runs (14 stalls, 13.4 s)**; same with the jitter fix compiled out (patched copy of egui-wgpu, `--config patch.crates-io`): **1/8 runs (1 stall, 0.75 s)**. Programmatic every-frame: base 2 and 21 stalls vs jitter-fix-off 0. Suggestive of the `presentsWithTransaction` path (hypothesis H1) but **n is small (Fisher exact ≈0.1 on 5/8 vs 1/8) → not proven**; the one remaining stall without the fix shows it is not the only path.
5. **Real mouse live-resize** (14 corner drags per run, 29 distinct window sizes, 100k and 1M rows): base build 8 runs/25,087 frames, jitter-fix-off 8 runs/24,153 frames, final build 6 runs/18,443 frames → **0 stalls > 100 ms in all 22 runs; worst frame interval 29 ms**; `ui()` CPU p95 0.53–0.58 ms.

**Root cause statement (what the data supports):** the ~1 s stalls are `nextDrawable` timeouts in the macOS CoreAnimation/wgpu present path, triggered by non-interactive resize (programmatic `InnerSize` each frame, or accessibility-API size changes) while the jitter-fix `presentsWithTransaction` mode is active. They are not caused by this app's rendering code and did **not** occur under real mouse-driven live resize. No app-code bug → no code fix and no regression test is possible at our seam (documented, per diagnosing-bugs "no correct seam" rule).
**Harness fix:** the `resize` scenario in `benchmarks/run_t003.py` (resize every frame) is now labelled STRESS in `summarize.py` and must not be used as the resize metric; the resize metric is `resize_mouse.py`. Dataset size (100k vs 1M) made no difference in any resize experiment.
**Not done:** no GPU-level profile (Metal System Trace/Instruments), no comparison with winit-only or native AppKit, no drag on a second display. Whether disabling the jitter fix causes visible live-resize jitter was **not evaluated** (no visual capture), so it is not recommended. Upstream issue not filed.

## Priority 2 — real input (CGEvent; state read from the app's own `--event-log`)
Tool: `benchmarks/tools/inject.swift` (keyboard incl. modifiers, Unicode text, click/drag/scroll) + `benchmarks/followup/e2e_input.py`. Needs Accessibility permission; it takes over the keyboard/mouse while running (~1 min).
**Final run on the final build: 35/35 checks passed** (`raw/final_e2e.log`). Covers: ASCII + Thai/combining-mark typing (as Unicode key events), Backspace, Shift+Left selection delete, Cmd+V paste (Thai+ASCII), Cmd+A replace, grid click selection, Down/Right, PageDown, Cmd+↑/↓, Home/End, Cmd+C copy (clipboard compared to `ลูกค้า 0`), mouse wheel, editor↔grid focus handoff in both directions (arrow keys reach only the focused pane; editor releases text focus after a grid click), F6, Alt+1/2/3, explorer click + arrows, tab open (+ button, Cmd+T), typing into the new tab, Ctrl+Tab / Ctrl+Shift+Tab / Cmd+W, tab click, editor/results splitter drag (grow + clamp), Cmd+Enter run and Esc cancel on the worker thread, Cmd+Shift+L theme.
**Real bugs found by this testing, now fixed with tests** (all in `0d4972d`):
| Bug | Evidence | Fix + regression test |
|---|---|---|
| F6 / Alt+1 / Alt+3 could not leave the editor (editor re-claimed focus the same frame) | E2E run 1: shortcut checks failed; run 2 after fix passed | `model::focus::FocusModel` + 6 unit tests (state machine of the per-frame ordering). Tests were red only against stubs; the original failure was demonstrated by the E2E run, not by a unit test |
| Ctrl+Shift+Tab acted as Ctrl+Tab (broader matcher consumed it) | headless test with the original matcher order: `next_tab: true` for Ctrl+Shift+Tab (red), then fixed (green) | `shortcuts::read` + 7 tests using synthetic egui input |
| Cmd+C never copied the grid cell (egui emits `Event::Copy`, not a key) | E2E: clipboard stayed `SENTINEL` | read `Event::Copy`; `grid::copy_text` test (full value, NULL→empty); wiring verified by E2E only |
| Event-log JSON invalid for Thai combining marks (`{:?}` → `\u{e47}`) | first E2E run silently skipped lines | `jsonlog::json_string` + 3 tests |
**Harness defects found and fixed (not app bugs):** keyboard events from a nil CGEventSource were dropped (now `hidSystemState` + 40 ms key hold); modifier flags leaked into subsequent Unicode typing (now cleared per event); a single wheel event was ignored (now 5 line-notches); one test expectation (`\n` is not a text event).
**NOT TESTED:** real Thai IME composition (injected Unicode events bypass it), VoiceOver, mouse drag-selection and double/triple-click in the editor, hand-dragged explorer panel width, trackpad momentum, external monitors/other scale factors, Windows/Linux. See `docs/evidence/T-003-manual-test-checklist.md`. Observed behaviour note: Backspace removes one code point, so a tone mark is deleted before its base consonant; whether that matches Thai users' expectation is unreviewed.

PERF-04 (≤50 ms p95 interaction) and PERF-05 (≤33 ms p95 scroll frame) are met on this machine by the interval/latency figures above, with the caveat of a non-baseline machine and an incomplete latency definition.
**Idle CPU outlier (earlier 4.01 s over 60 s ≈ 6.7 %):** time series of that run shows a sustained ≈0.2 CPU-s per second for 12+ s starting at t≈8 s, i.e. continuous repainting. Reproduction attempts: 8 idle runs ×40 s + 3×60 s all at 0.72–0.78 % except one with two 0.12 s bursts (sampled: main thread 91 % idle in `mach_msg`, 9 % in repaint). Pointer test (`raw/idle_pointer_test.txt`): pointer outside window or parked over it 0.80 %; **jiggling the pointer over the window at ≈27 moves/s → 8.4 %** (egui repaints on every pointer move), which extrapolates to the observed ≈20 % at typical mouse event rates. Most likely cause: pointer activity over the window during that run — **consistent with the data, not proven for the original run**. Steady idle ≈0.75 % comes from the focused editor's caret-blink wakeups (not isolated by an experiment).
**Unexplained anomalies (reported, not hidden):** 2 of the first 8 latency runs showed a multi-second input gap (one 6.4 s, keys applied later in a burst; the other lost 21 of 100 matches). Not reproducible in 9 later runs (3 under `sample`, 6 final). Cause undiagnosed (hypotheses: window occlusion/focus loss from other desktop activity, or the same drawable timeout; neither verified). Startup run 1 is consistently ≈4× slower (749–830 ms).

## Known limitations / risks (delta)
- Resize stalls exist for non-interactive resize on macOS/egui-wgpu; root-cause mechanism evidenced, H1 not proven; no mitigation shipped.
- Latency figure is app-side only; no end-to-end scan-out latency; one unexplained multi-second input stall class.
- E2E/benchmark tooling drives real input on the developer's machine and requires Accessibility permission.
- Single machine, battery power, macOS only; Windows baseline and 150 % scaling untested.
- Accessibility and Thai IME unverified; font redistribution unresolved.
